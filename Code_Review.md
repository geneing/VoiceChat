# VoiceChat architecture review

The app keeps text and voice on one realtime session. `AppViewModel` owns chat selection, persistence and the UI-facing state. `RealtimeSession` owns the protocol, turn state, reconnect and tool continuations. The transports own media and deliver parsed control events. `ReasoningClient` streams a separate, on-demand text completion and hands the result back to the realtime turn. That split is worth preserving. The main synchronization gaps are at the boundaries between the media callback, realtime response, and asynchronous tool completion.

## Findings in priority order

1. **P1 · Barge-in can sit behind a network tool.** `handleEvent` holds the session mutex while `handleFunctionCall` awaits ordinary tools. A slow search, location fix or weather request can delay speech-start handling and the interrupt button. The WebSocket callback puts PCM directly into the player while speech-start goes through the collector. It also unmutes unconditionally on `ResponseCreated`, before the session can enforce text-only playback. The player checks mute once per dequeued chunk, so a chunk already in a blocking write loop can race a flush. Give playback a transport-local interruption gate tied to the active response and modality, and move all slow tool work outside the mutex. Exercise this across WebSocket, WebRTC and AOQ. [Session event handling](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L829) · [WebSocket playback](app/src/main/java/com/voicechat/assistant/realtime/ws/WebSocketTransport.kt#L211) · [PCM writer](app/src/main/java/com/voicechat/assistant/realtime/audio/PcmPlayer.kt#L136)

2. **P1 · Deep-reasoning and tool results can cross turn boundaries.** Typed pre-reasoning releases the lock and shares mutable job and outcome fields with the voice handoff. A second typed send can replace those fields while the first send is suspended. Async handoff and news completions use the current transport and modality when they return. Late server completion/cancellation events also update the shared response buffer without checking which response owns it. Introduce a session generation and turn ID, and carry them through every job, result and chat write. Associate server response IDs with their originating turn. Apply completions only to matching live work, and make an explicit second-send policy. Voice barge-in should preempt that turn immediately. [Typed send](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L564) · [Handoff completion](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L1251) · [Response events](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L950)

3. **P1 · Mixed tools can request multiple continuations or resume too soon.** A single `toolOutputsSent` flag records that *some* output exists. If a quick tool returns before `response.done` and deep reasoning or news returns later, the quick output can trigger the next response while the other job is still pending. A later completion can start another response, especially in the gap before `response.created`. Track pending call IDs per parent response. Send each output once and guard the continuation with a single transition after the parent response completes and every registered call has a result, including errors. Keep the UI in a thinking state while required tool results are pending. [Response completion](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L950) · [Tool dispatch](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L1113)

4. **P1 · Critical events share a lossy queue with streaming data.** All three transports use a bounded `SharedFlow` configured with `DROP_OLDEST`. A burst while the collector waits for the mutex can evict speech, tool, response or disconnect events. A lost terminal event can leave the session thinking indefinitely. Keep a bounded, ordered control inbox with visible overflow recovery, and coalesce high-volume updates separately. If transcript deltas are coalesced, retain their accumulated text or recover from an authoritative final snapshot. Budget the PCM queue by milliseconds and count discarded audio. [WebSocket queue](app/src/main/java/com/voicechat/assistant/realtime/ws/WebSocketTransport.kt#L52) · [WebRTC queue](app/src/main/java/com/voicechat/assistant/realtime/webrtc/WebRtcTransport.kt#L70) · [AOQ queue](app/src/main/java/com/voicechat/assistant/realtime/aoq/AoqTransport.kt#L66)

5. **P2 · Reasoning cancellation can wait for a blocked read.** The HTTP stream uses blocking OkHttp reads on `Dispatchers.IO`. Its `Job.invokeOnCompletion` handler runs when the job completes, so it cannot be relied on to interrupt a silent socket while the job is still inside that read. Bind the owning coroutine’s cancellation to the individual `Call.cancel()` at suspension time. When a warm result is adopted, carry its operation identity and cancellation ownership with it, and check the required depth alongside transcript overlap. [HTTP stream](app/src/main/java/com/voicechat/assistant/realtime/handoff/ReasoningClient.kt#L116) · [Warm-result adoption](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L1215)

6. **P2 · Send failures and chat switches can leave inconsistent history.** A typed send appends the user row before session dispatch. `dispatchTextTurn` logs rejected sends and still returns success, even if the batch failed partway through. Session callbacks also resolve the current chat after launching work, so a chat switch can redirect a late write. Pass the originating chat ID with the turn, and surface dispatch failure to the row and UI. For recovery after a partial write, use an explicit retry policy that avoids duplicating an accepted item. [Typed entry point](app/src/main/java/com/voicechat/assistant/ui/AppViewModel.kt#L306) · [Dispatch](app/src/main/java/com/voicechat/assistant/realtime/RealtimeSession.kt#L641) · [Assistant persistence](app/src/main/java/com/voicechat/assistant/ui/AppViewModel.kt#L665)

## Verification for the proposed changes

Start with a fake transport and a controllable reasoning stream. Test barge-in while search and SSE are stalled, two typed sends while pre-reasoning is pending, two tools finishing on opposite sides of `response.done`, an old response ending after a new turn starts, a reconnect with a late tool result, and a full event queue. Check that each surviving turn resumes once, stale work cannot speak or write into another chat, and the speaker stays muted for typed turns. Then measure speech-start-to-silence on-device for each transport, including a Bluetooth route change.
